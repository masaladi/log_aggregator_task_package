# 判分粒度设计说明（scoring rationale）

## 判分结构

本题 verifier（`tests/test.sh`）的 reward 由 **3 个二元项**构成，每项权重 1/3：

| 项 | 覆盖范围 |
|---|---|
| ITEM 1 | HTTP 协议与端点：`/healthz`、`/api/v1/aggregate` 结构与紧凑输出、404、405+`Allow`、HEAD 语义、查询串、自定义响应头、Content-Length |
| ITEM 2 | 聚合正确性 + 增量 SLA（变更后首请求 ≤1.5s）+ 写入中途（未提交尾行）+ 截断/就地重写回退 |
| ITEM 3 | 运维真实性（logsvc 身份 + venv 解释器 + 9090 socket 归属 + 遗留抢占/看护进程清零，对应题面运维规范 4 的"清理必须彻底"）+ 日志轮转（含轮转期间并发不撕裂）+ 20 并发响应与真值全量一致 + `fcntl.flock` 等锁上限与快照回退 |

可能取值：`0 / 0.33 / 0.67 / 1.00`。

## 为什么是 3 项二元，而不是更细的连续计分

本约束来自难度门的判定口径：**筛选模型得分必须 ≤ 0.700**。在该口径下，判分结构必须满足两条性质：

1. **任何单项失败都必须把总分压到 0.700 以下**（否则模型漏掉一个能力维度仍能过线，难度门失效）；
2. **全对才是 1.00**（完整实现必须可被明确识别）。

设项数为 n、每项权重 1/n，则"任一单项失败后剩余总分"为 `(n-1)/n`。要求 `(n-1)/n ≤ 0.700` 解得 `n ≥ 3.33`，即 **n ≤ 3** 时才能保证"错任意一项即 ≤ 0.67"；同时 n ≥ 2 才能区分"什么都没做（0）"与"做了一部分（0.33）"。**n = 3 是同时满足两条性质的最优解。**

若改为 6 项均分，错 1 项得 0.833 > 0.700——存在"漏掉任意一个能力维度仍通过难度门"的通道，这正是本项目早期版本（6 项结构）被淘汰的原因。

若改为项内连续计分（例如 ITEM 2 内 5 个子场景按通过比例给分），一个漏掉 1 个子场景的实现可得 `(1 + 0.8 + 1)/3 ≈ 0.93`，部分实现反而更容易过线，与难度门方向相反。

## 每项内部为何是"全有或全无"

三项各自代表一个**不可分割的工程能力面**（协议实现 / 增量正确性 / 运维与并发真实场景）。项内任一子场景失败即判定该项未达标：以 ITEM 2 为例，"算得快但半行多算 1 行"与"算得对但每次全量重解析"在 生产语义下同样是不可接受的交付，二元判定与真实运维的验收口径一致。

## 与环境参数的绑定

- 数据文件基线约 900 万行 / 880 MB（`environment/gen_baseline.py`），单核 stdlib `json.loads` 全量实测约 22-31s、增量解析 0.002s——1.5s 门槛使增量成为唯一可行路径；镜像经 apt 预装 ujson（高性能 JSON 解析库，实测全量约 12-13s），首次请求宽限 24s 与结构变更宽限 30s 构成双性能门：stdlib 逐行实现（建态约 28-31s、全量重扫约 30s）两条门均无法通过，必须采用高性能解析与增量解析的组合。实测方法、多轮数据与复现命令见包根目录 `benchmarks.md`；
- 20 并发（ITEM 3）确保并发合并（single-flight 类机制）是必需而非可选；
- `flock` 等锁 1 秒上限 + 5 秒长持锁写入，确保"超时回退快照"被真实执行。
